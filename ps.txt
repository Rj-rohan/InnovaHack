THE KILL SWITCH
Problem Statement — Fintech

================================================================================
BACKGROUND
================================================================================

Autonomous agents are increasingly given wallets and allowed to transact without
a human approving each individual move. This unlocks speed and autonomy — but it
also means a compromised, buggy, or simply overzealous agent can spend money
faster than any human can react.

================================================================================
THE PAIN POINT
================================================================================

Once an agent holds a wallet, "asking it nicely" to behave isn't a control — it's
a hope. There's no reliable way today to cap what an agent can spend, restrict who
it can pay, or stop it mid-transaction if something goes wrong, because most
controls live in the agent's own logic rather than being enforced independently
of it.

================================================================================
CORE REQUIREMENTS
================================================================================

1. Spend limits enforced at the wallet or contract layer — not inside the agent's
   own logic.

2. Allowlisted counterparties, so the agent can only transact with pre-approved
   parties.

3. An owner-controlled mechanism to freeze the agent mid-execution, at any point.

4. A demo showing the agent running unsupervised, attempting to exceed its policy,
   and being blocked.

================================================================================
EVALUATION METRICS
================================================================================

Enforcement layer
    Whether controls are genuinely enforced at the wallet/contract level,
    independent of the agent's cooperation.

Kill-switch reliability
    How immediately and reliably the owner can freeze or revoke the agent.

Attack resistance
    How well the system holds up when the agent actively tries to exceed its
    limits.

In-flight revocation (bonus)
    Whether access can be revoked while a transaction is already in progress.

Real-world plausibility
    Whether the guardrails would hold up with a real wallet and real funds, not
    just in a controlled demo.


================================================================================
HOW THIS BUILD ANSWERS EACH REQUIREMENT
================================================================================

Requirement 1 — spend limits at the contract layer
    AgentWallet.sol holds a per-transaction cap and a rolling 24-hour cap in
    contract storage, checked inside pay() before any transfer. The rolling cap
    is a real trailing window (a 32-slot ring buffer), not a calendar day that
    resets at midnight and lets an agent spend two full allowances an hour apart.
    The agent's own code performs ZERO validation — server/chain/client.py
    send_payment() signs and broadcasts whatever the model asked for, and says so
    in a comment. The verification tools the agent has (purchase-order matching,
    duplicate detection, vendor history) are advisory: it can call all of them,
    ignore every answer, and still broadcast.

Requirement 2 — allowlisted counterparties
    An on-chain mapping of address to category tag, owner-writable only. Any
    payment to an unregistered address reverts with CounterpartyNotAllowed.
    Categories let the owner disable a whole group ("vendor", "gas") in one
    transaction rather than address by address.

Requirement 3 — owner freeze, mid-execution
    pause() is owner-only and re-checked before every payment leg. It is
    deliberately NOT nonReentrant, so it still works when called from inside a
    payment run already underway. A throttle setting gives a middle position
    between running and frozen. ownerWithdraw() bypasses the freeze, so a paused
    wallet never locks the owner out of their own funds. The owner signs from
    their own wallet, so the machine running the agent provably cannot unfreeze
    itself — and the service refuses to start if the agent's session key equals
    the owner address.

Requirement 4 — unsupervised agent, attempting to exceed policy, blocked
    A FastAPI agent runs on a timer, reviewing an invoice queue and deciding for
    itself what to pay, hold, or ignore. Three demo scenarios:
      A  normal operation — verifies a purchase order and pays within the caps
      B  the agent is compromised — subverted instructions plus a poisoned
         invoice; it decides to pay an attacker and the chain refuses
      C  freeze mid-flight — a multi-leg run halted partway through by the owner

    Scenario B has a second form with the model removed entirely (a ~30-line
    script that signs directly). The contract cannot tell whether a transaction
    came from a careful model, a subverted one, a rogue script, or an attacker
    holding a leaked session key. It refuses all four identically, because it
    never asks.

Bonus — in-flight revocation
    payBatch() re-validates pause state, session validity, the allowlist and both
    caps before EVERY leg. Proven by test_BatchHaltsMidFlightWhenPausedBetweenLegs,
    which uses a re-entrant token to pull the kill switch between legs of a single
    transaction — something no live chain can demonstrate.

Real-world plausibility
    The agent holds a revocable session key that can only propose payments; it
    cannot pause, unpause, change limits, edit the allowlist, or withdraw. The
    owner key is absent from the agent process entirely. The demo runs on a local
    chain for speed and reliability, but the same bytecode deploys to a public
    testnet by changing two environment variables — no code changes.

    Nothing in the demo is a fixture: vendors, purchase orders, invoice numbers,
    amounts and memo text are generated by an LLM at the start of each run. Run it
    twice and the book of business is different both times.

================================================================================
WHAT IS DELIBERATELY NOT A CONTROL
================================================================================

The agent can hold a suspicious invoice for human review. That is good product
behaviour and it is NOT the safety mechanism — a compromised agent simply would
not use it. If a reviewer comes away believing the agent's own caution is what
protects the money, the demonstration has failed. The contract is the control;
scenario B exists to make that unmistakable.
